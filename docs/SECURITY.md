# 安全模型与防护边界

本文档说明 `dns-guard-stack` 假定的威胁模型、核心设计原则、开发过程中修正过的真实缺陷类型，以及系统明确不覆盖的安全边界。

---

## 1. 威胁模型

### 我们防御的攻击面

* **上游路径投毒与抢答**：攻击者在上游网络链路上注入或抢先投递伪造 DNS 应答。
* **不可信的国内上游**：国内 DoT 运营方不保证端到端 DNSSEC 语义，且存在对不存在域名返回伪造地址的风险。
* **社区名单数据源污染**：第三方分流名单（如 `v2fly` 等镜像源）出现误分类或被上游污染。
* **公网入口滥用**：对公网 DoT（`:853`）与 DoH（`:444`）接口的扫描、突发请求及资源耗尽。

### 不在防御假设内

* 攻击者已取得宿主机 `root` 权限（本机一切防护均失效）。
* TLS 1.2+ / 1.3 密码学或证书校验被攻破。
* 权威域名的 DNSSEC 私钥泄露。

### 核心目标（按优先级）

1. **宁可失败，不给假答案**：无法验证或核对不过时返回 `SERVFAIL`，不降级明文。
2. **故障隔离**：单一上游或名单错误不能导致整类域名被整体改道至低可信路径。
3. **变更可追溯、可回滚**：所有代码发布与名单更新均有校验、指纹与回滚点。

## 2. 设计原则与落地机制

| 原则 | 实现方式 |
| :--- | :--- |
| 宁失败不给假 | `Unbound A` 设 `forward-first: no`（禁止回退明文递归）；验签失败返回 `SERVFAIL`；国内见证不过则回退 `A` / `alt` 或返回 `SERVFAIL`。 |
| 信任只降不升 | 上游自称 `AD=1` 但无本机可验证签名时，仅归入 `ACCEPTED`（上限 300s），不能升格为 `SECURE`（上限 900s）。 |
| 最小信任面 | 默认 `CN_TRUST_MODE=known`，仅国别后缀与人工白名单免见证，其余国内域名一律交叉核对。 |
| 数据变化即失效 | 准入缓存绑定名单代次（`typed` / `veto` / `exc` / `allow` 哈希前缀），任一名单变更即失效相关缓存。 |
| 原子变更与回滚 | 发布切换采用软链 + 双进程同时重启 + 门禁轮询；`iptables` 采用计算后单次 `restore`；名单写入采用临时文件 + `os.replace`。 |
| 纵深防御 | 全加密上游（DoT/DoQ/DNSCrypt）+ UDP 报文绑定校验 + `iptables` 封堵明文 `53` 出口 + 单源限速 + 独立 `verifier` 进程。 |

## 3. 演进过程中修过的典型缺陷

这些曾在实际测试或审计中暴露的问题，解释了当前代码为何采用看似严格的防御写法：

| 缺陷类别 | 曾出现的症状 | 修正方案 |
| :--- | :--- | :--- |
| 缓存不老化 | 驻留 299s 的 300s 条目仍按完整 300s 下发给客户端 | 改为逐 RR 老化并按剩余生命期裁剪 `max_ttl`；零 TTL 不写入可复用缓存。 |
| 失败语义过粗 | 任意 `rcode=2` 均被判为 DNSSEC 失败，导致普通传输超时无法走备用通道 | 仅当 `OPT EDE code=15` 且 `value ∈ 6..12` 时判定为 DNSSEC 失败，其余按传输问题允许重试。 |
| 应答绑定缺失 | UDP 回包未严格校验 ID 与问题段，存在抢先注入风险 | 校验 ID/QR/opcode/QDCOUNT、`QNAME+QTYPE+QCLASS` 三元组、RR 计数及报文尾长；使用 `connect()` 固定对端。 |
| 双进程发布错配 | `guard` 与 `verifier` 运行在不同版本，策略语义不一致 | 进程间握手携带 `release_id` 与代码哈希指纹，不匹配直接拒绝执行。 |
| 路由与信任耦合 | 单份社区名单同时决定分流与免检，导致境外 CDN 被国内化后直接放行 | 拆分为 `is_cn_domain()` 与 `is_cn_trusted()` 两层，配合例外名单兜底。 |
| 撤销名单后缓存残留 | 将域名移出白名单后，旧答案仍在缓存中继续下发 | 缓存键绑定名单代次，并提供 `cn-trust-revoke.sh` + `agh-cache-clear.sh` 联动清理。 |
| 冷启动降级过宽 | 名单不可用时退回宽匹配，等同扩大了国内信任面 | 优先读取同目录快照；仍缺失时一律判为非国内，拒绝宽匹配。 |
| 只读检查有副作用 | 执行 `--check` 时实际重写了防火墙规则 | 只读分支在所有写操作前提前返回，写入函数在只读模式下直接报错退出。 |
| 探针自身失真 | 探针跳过证书校验、把 `NOTIMP` 当健康、读 `AD` 不带 `DO` | 强制严格 TLS + 显式 SNI，按样本类型严格断言（`dnssec-failed.org` 必须返回 `SERVFAIL`）。 |

## 4. 明确的边界与局限

* **单机部署，非高可用**：宿主机、公网入口容器、`dnsdist`、Docker 网络及 TLS 证书均为单点。本栈提供纵深防御，抗整机故障需要多机多入口架构。
* **默认无用户级鉴权**：公网入口按公共解析模式设计（依赖限速与共享准入池）。若仅限个人或家庭使用，建议在 `adgh` 中配置 `allowed_clients` 或叠加防火墙/隧道限制。
* **上游社区名单无官方签名**：`v2fly` / `clang.cn` 数据源本身无密码学签名，本栈仅能保证名单"落盘归档后未被篡改"（SHA256 + GPG 归档）。
* **国内域名缺乏 DNSSEC**：国内路径的答案依赖交叉见证、否决名单与特征检查，不能提供与 DNSSEC 同等的密码学证明。
* **多源共谋限制**：如果多个独立运营方同时返回完全相同的伪造结果，共识模型无法识别并会采纳该答案。

## 5. 验证安全机制是否生效

```bash
# 1. DNSSEC 验签失败样本：应返回 SERVFAIL
dig @127.0.0.1 -p 853 +tls +dnssec dnssec-failed.org

# 2. DNSSEC 正常签名样本：应返回 NOERROR 且带 ad 标志
dig @127.0.0.1 -p 853 +tls +dnssec cloudflare.com

# 3. 国内分流可用性：应正常解析
dig @127.0.0.1 -p 853 +tls www.qq.com

# 4. 查看名单与见证统计
python3 -c "import json; print({k:v for k,v in json.load(open('/opt/dnsguard/stats.json')).items() if k.startswith(('cn_trust','cn_dom','cn_typed','cn_veto'))})"

# 5. 双进程发布一致性与名单归档验签
python3 /opt/dnsguard/tools/release_consistency.py; echo "rc=$?"
python3 /opt/dnsguard/tools/verify-cn-lists.py
```
